# Audi Connect V3 — user guide

**Configure → Discover → Use.** V3 is experimental and opt-in within Audi Connect. V2 remains the default and fallback. Keep one account, one config entry and the existing HA devices and entity IDs.

Use a [published test release](https://github.com/npinguin/audi_connect_ha/releases) containing V3.

## User guide

### Installation and rollback

Follow the [main README](../readme.md) for installation and sign-in. Back up Home Assistant before upgrading. In **Settings → Devices & services → Audi Connect → Configure**, choose V3 and keep the normal scan interval (minimum 15 minutes). Save and reopen Configure after the runtime reloads. V3 configuration uses five independent choices: **General settings** (runtime, polling and vehicle filter), **Vehicle setup & discovery** (guided or specific function tests), **Additional data sources** (EU Data Act and reverse geocoding), **Service & maintenance** (local dealer details), and **Advanced & experimental** (charging STOP recovery and Development Workbench). Each settings page saves independently. Disabled optional features hide their extra settings; reopening Configure never dispatches a vehicle command. Leave optional sources and experimental features disabled unless needed.

V3 enumerates vehicles during setup; the V2-only startup update preference is retained for rollback. To revert, select V2 in the same entry and reload. Do not delete the integration or the registry to resolve a temporary data problem. Retain device IDs, entity IDs, user preferences and trip history. Verify automations after any runtime change.

### Audi Connect — daily vehicle management

The Audi Connect sidebar follows the owner-approved vehicle-first visual reference: My garage, vehicle identity and image where available, direct function tabs (Overview, Charging, Climate, Access, Location, Trips, Service, Vehicle), and a Settings icon. Overview groups battery and fuel, quick actions, vehicle status and service information. No intermediate menu is required. It is independent of the optional Engineering Workbench. Status and useful actions come first, context-specific settings next, and additional native detail is available on demand. Choose an available vehicle; only data and controls that Home Assistant grants the signed-in user for that vehicle may appear. Use the normal dashboard to understand status, perform actions, edit supported vehicle settings and inspect history, without knowing API families or enabling engineering.

| Journey             | Expected outcome                                                                                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Overview            | Vehicle identity/image where available, actual freshness, range, charge/fuel, security and health, with contextual quick actions.                                                    |
| Charging            | Actual state, plug, power, range, ETA, charging targets, active profile, current and mode; operate the existing native controls.                                                     |
| Climate             | Actual climate state, target temperature, supported zones/heating and existing timer information; change supported native settings and actions.                                      |
| Access & Security   | Door/window/lock state and supported actions; distinguish unknown and last-known from secure.                                                                                        |
| Location            | Last reported parking location/time and native tracker; never describe a retained position as live.                                                                                  |
| Trips & Consumption | Native trip statistics and existing scoped archive, paginated details and bounded export with appropriate access.                                                                    |
| Service & Health    | Native inspection/oil/tyre data and existing local dealer, appointment and warranty settings (editable directly by administrators).                                                  |
| Vehicle & Documents | Model/year/image/powertrain and verified source data; official manual in the interface language, myAudi and Data Act links without sending VIN in URLs.                              |
| Settings            | Existing HA configuration flow for account options, data sources, service details and explicit discovery; preserve configuration permissions and native device/automation workflows. |

The UI uses Home Assistant entities and the existing command owner, including native configuration and control dialogs. Service preferences use the same validated config-entry options as the native configuration flow. Existing read-only timer observations are displayed without inventing timer-write support. Parking uses the existing Home Assistant tracker and map; trip charts show recorded trips only. A service call returning successfully does not establish physical execution. Use reported capture, actual readback and command feedback; no optimistic success in the dashboard itself. Unavailable or unsupported functions are not invented; unknown measurements remain unknown. Additional factory data, service history and recalls require authorized source evidence before integration. No separate data store, API poller or command engine.

The normal vehicle panel and the optional engineering panel must not prevent native entity setup or service operation if frontend registration fails. Editing only V3 local dealer and service preferences updates the existing config entry and native local projections without an OEM poll or account reload; other settings retain the existing reload behavior. On registry changes, revalidate access before allowing actions, retain drafts for the same still-authorized vehicle and discard them on loss of scope. The overview identifies retained manufacturer/registry identity, and reported status retains its own capture/quality. Read-only schedules include reported recurrence, charging windows and linked climate preference when present, using the existing native detail envelopes even if one presentation entity is unavailable. Missing fields remain unknown; no schedule write is inferred.

Daily use should present one obvious native action or setting per function, with status and readback visible beside it. An unrelated HA state update must not discard an active editor, move keyboard focus or conceal newer safety-relevant status. An explicit refresh of the view is local; cloud refresh and vehicle refresh/wake are separate native actions only when offered. Settings links lead to the owning account and device; local service preferences are directly accessible. User-facing labels, native option labels, dates and measurement times use the selected language where supported. The trip archive can be filtered by an inclusive start date and exclusive end date in UTC, with pagination and JSON/CSV exports covering the same selected period (not merely the current page). Period totals describe observed archive records only; missing measurements remain missing, zero is retained and coverage counts distinguish incomplete totals. No new Audi requests or archive storage are required. Changing vehicle, losing permission or disconnecting invalidates scope before displaying asynchronous results or dispatching actions. A late unrelated success must not clear an observed server cooldown; only the reserved recovery request may clear it.

Engineering Workbench remains separately opt-in and administrator-only. It retains discovery, mapping, API evidence and activation workflows. Verify read/control denial, multiple accounts/vehicles, state updates, one intentional action, configuration save/readback, history/export, mobile/tablet/desktop, dark/light themes, disabled entities, unload/restart and V2 rollback; keep native HA entities and automations usable independently.

### Data and freshness

Audi's cloud can be reachable while a parked vehicle has not sent new data. A cloud refresh is not proof of a new vehicle capture. No automatic wake on every poll.

| State          | Meaning                                                                                                                                 |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Fresh          | Valid measurement with a sufficiently recent vehicle capture.                                                                           |
| Last known     | Historical observation; check its capture time. Not confirmation of current state.                                                      |
| Unknown        | No reliable current value. A historical value may still be available in attributes.                                                     |
| Unavailable    | The entity or source cannot currently provide a usable value. Check the reason.                                                         |
| Not applicable | The underlying condition does not apply, e.g. charging ETA when explicitly not charging. Never interpret a missing ETA as zero minutes. |

Latest vehicle data age refers to the newest usable vehicle measurement, not the cloud receipt or oldest measurement. Oldest observed age and per-job ages remain available in attributes and the Workbench. Check the specific entity's capture time for automations. HA state update time is not the original capture time, including when a last-known value is retained. A vehicle-specific native enrollment refusal (Audi error 2104) defers native requests for six hours; other vehicles and the optional Data Act channel remain independent. Known plug-in vehicles retain plug entity identities even if the OEM omits plug status; missing data does not mean disconnected. The Service overview can expose explicit tyre warning evidence; absence of such evidence is not proof of healthy tyres. Data Act delivery may be fresh while the underlying capture is old. The tracker shows last parked position, not live GPS; movement without reliable vehicle capture stays unknown.

Previously registered, mapped read-only sensors and reviewed native control identities are offered again on reload even if their current OEM value or write route is absent. Registration is not authorization. The same entity recovers when valid evidence returns. Its identity does not establish current availability or new vehicle support. Explicitly retired identities such as the redundant V3 Charging ready sensor remain retired; no registry deletion is required.

Two optional native diagnostic readings, Safelock active and Charge power limitation reason, are mapped only when the vehicle reports the matching typed value. The app schema is reference evidence, not proof of vehicle support. The limitation token is reported without inventing a reason or changing a command.

### Optional parking address

**Parked in** continues to use Home Assistant zones locally. A separate **Parking address** sensor can resolve the last reported parked coordinates when **Reverse geocoding** is explicitly enabled under **Additional data sources → Reverse geocoding** (off by default). Supply an authorized HTTPS Nominatim-compatible reverse endpoint, for example a self-hosted service; the public OpenStreetMap Nominatim endpoint is not supported for vehicle tracking. Only rounded coordinates (three decimal places) are sent, without Audi credentials or identifiers. The address is approximate, not live GPS. OpenStreetMap data attribution: [© OpenStreetMap contributors](https://www.openstreetmap.org/copyright). See the [public Nominatim usage policy](https://operations.osmfoundation.org/policies/nominatim/) for the distinction between public and self-hosted services.

The optional lookup uses the existing parked position and does not wake the vehicle, add Audi requests or change native polling. Results are cached in memory, not in Audi diagnostics or profile storage. Home Assistant may record the address entity in its own history; exclude it from Recorder if that is not desired. Disable the toggle to stop external requests and hide the resolved address; historical HA recorder data is not automatically deleted. The existing device tracker remains the native map view.

### Native controls

Use the HA vehicle device page for ordinary actions. Routes and features depend on the vehicle, auth context and verified capabilities. Missing controls are not permission to try a different API.

- Stateful controls other than charging can show explicitly marked optimistic requested state for at most five minutes from dispatch after known HTTP acceptance. This is not physical confirmation. Newer valid captures, rejection or a superseding command end that overlay. After acceptance, expiry or restart without a newer valid capture leaves the effective control state unknown; the last reported state and command feedback remain separately available. Check `state_is_optimistic`, `state_source`, `last_reported_state`, capture and command outcome. Charging START/STOP keeps the reported state (marked last-known when older than the accepted command) or unknown if no reading exists. Read-only telemetry never projects command intent. A staged local temperature is an edit, not an applied temperature.
- HTTP 2xx means backend acceptance, not physical execution. A matching later capture is recorded separately as `command_readback_observed_at`; it does not turn an accepted command into a verified command. A matching state can result from myAudi, a timer or manual operation. Correlated OEM failure takes precedence over earlier acceptance. Never automatically replay an uncertain command, including a disconnected HTTP write or an incomplete response. With **Advanced & experimental → Charging STOP recovery → Retry failed charging STOP** explicitly enabled (off by default), a direct CARIAD STOP may receive one recovery attempt only after an exact backend timeout and a new native still-charging observation; no retry for pending, missing or ambiguous outcomes, after restart or after another command. Charging captures more than five minutes after dispatch are telemetry, not command readback. Configure confirmation timeout (60–300 seconds), verification poll interval (30–120 seconds), verification window (30–300 seconds), zero or one additional STOP, and the final notification. Both attempts use bounded read-only checks (at most ten single-job charging GETs each), stopping on fresh evidence or quota limits. The final notification, enabled by default, also reports a failed or unconfirmed original STOP when no retry is sent. No third automatic request is sent. Routine command history is not discovery evidence or an interlock: retain verified routes across temporary failures and restart, and allow a new explicit request after the existing bounded cooldown. Only an explicit discovery experiment awaits physical review; authorization and parameter/prerequisite checks remain in force.
- Climate has separate read target, stored-settings start, temperature-bearing start, independent settings update and stop operations. The configured temperature can be readable even when no temperature-write route works. Temperature adjustment requires an enabled applicable write route selected by the resolver. A reviewed catalog match is not the same as local physical verification; an alternative route must be verified before activation. Availability depends on your vehicle.

- **Location AC charging current** is separate from the global charge setting and appears after the current location reports `max` or `reduced` and its separate discovery test is physically confirmed. The existing profile update reads the whole profile, rejects ambiguous IDs or a changed active location and changes only the current field. Verify the same profile and measured charging power; the native select reports the observed option rather than an optimistic requested value. A matching native readback must belong to the exact requested active profile and a newer capture; it is not proof of physical execution.

### Optional EU Data Act

Obtain an authorized continuous request in Audi's official portal. In V3 options, select **Additional data sources → EU Data Act**; enter portal credentials locally when required. The wizard and vehicle diagnostic show delivery status independently from native Audi health. Keep current connection does not reauthenticate.

Connected means a delivered or acknowledged unchanged dataset, not fresh vehicle data. Awaiting data means no confirmed delivery; subscription unavailable or access denied means check the portal request; authorization required means check credentials; rate limited means allow automatic recovery. Disconnect removes local optional credentials and observations without changing native Audi login or the portal request. Data Act is read-only; it never authorizes or confirms commands. During sign-in, the optional marketing question may be skipped once using the identity provider's reviewed Not now route; no marketing or data-sharing consent is granted. If interactive authorization is still required, complete it yourself in the official portal. The existing Data Act status entity shows the creation time of the last acknowledged portal file and the number of distinct newer empty-file notices in the last valid listing, when known. Neither is a vehicle capture timestamp. An empty listing or notice does not erase previously observed vehicle data; revoked access or a removed subscription still withdraws optional observations. No file names or identifiers are exposed.

## Engineering Workbench

Enable the optional V3 Development Workbench under **Advanced & experimental → Development Workbench** as an HA administrator. Open **Audi Engineering Dashboard**, select the account and vehicle. Ordinary HA use does not require the Workbench.

- **Overview**: current findings, health and vehicle capture. Use **Download trip archive (JSON)** to export the selected vehicle's complete locally observed completed-trip archive (up to 10,000 records) in a single read-only snapshot, without an Audi request or Recorder history export. It contains private trip times, distances and consumption, not raw payloads, VIN or trip IDs; keep the file private. A zero-record archive is valid; it does not imply that the vehicle has never travelled.
- **Capabilities**: compare source mappings, actual observations, supported actions and their HA entities.
- **Configure & test**: inspect an individual API route, its parameters and evidence; explicitly test or activate reviewed mappings.
- **API Log**: inspect bounded local request/response evidence and read-only scans.
- **End-user validation**: Guided walks eligible unverified actions; Expert selective lets you choose a capability or one action, including retesting eligible verified actions. Both use the same reviewed definitions, parameters and physical confirmation.

### Test a specific climate function

For ordinary users: Configure → Vehicle setup & discovery → select a specific function (or Guided). Both native setup and the Workbench use the same typed inputs and physical consent. The optional Workbench offers deeper evidence:

1. Safely park the vehicle, select it in the Workbench and open **End-user validation → Expert selective**. Filter by Climate.
2. To test stored settings, start with climate off; select Start cabin climate and confirm whether it really starts.
3. Stop climate, then select Start climate with temperature. Enter a different target temperature in °C. Verify both actual start and the requested target.
4. To test Change climate target temperature independently, start with climate off; choose a different target and verify it changes without starting climate.
5. Confirm Worked on vehicle or Did not work on vehicle for the actual outcome. If unsure, keep the test pending and inspect the car; do not replay it. Restore the vehicle to a safe state before the next test.
6. Check the native HA climate entity after validation. Only explicit physical confirmation activates a tested control route. A successfully verified route is stored for that vehicle; failure on another vehicle does not authorize or disable this one.

The same physical instructions appear in Guided. If undated charging-mode option lists conflict, they never become ordered vehicle measurements. Use Vehicle setup & discovery → Verify preferred charging mode to physically test Manual and Timer separately. A valid native options list is authoritative; temporarily missing, empty or invalid options may retain only individually verified modes on the active route revision. Explicit invalidation of route proof or capability impairment remains binding. A selectable option is not proof of the currently reported mode. A reviewed equivalent route may be tried after definitive rejection under the existing consent and quota rules; never auto-send a different semantic action.

### Report a problem safely

Include the exact integration/HA version, vehicle model/year/powertrain and market (if known), action, local timestamp with time zone, expected versus actual outcome, and myAudi/physical evidence if relevant. Compare historical and current builds only when the conditions and operation are known.

Download integration diagnostics from **Settings → Devices & services → Audi Connect → three-dot menu → Download diagnostics**. The integration's own data is designed to exclude credentials, tokens, VINs, coordinates, raw payloads and private trip values. The surrounding HA export can contain unrelated system or integration information: review it and share only the sanitized Audi Connect data section. Attach a ZIP if GitHub refuses the JSON. Do not share complete HA logs, raw responses, OAuth callback URLs or secrets.

The optional refresh-after-action setting requests at most one additional eligible vehicle refresh after known HTTP acceptance, including unconfirmed acceptance when no newer native capture has arrived. It does not repeat the original command and respects the existing wake budget and authorization. A cloud refresh still does not guarantee a newer vehicle capture.

Diagnostics are read-only and do not wake the vehicle. They distinguish transport requests, coordinator attempts, cloud reachability, vehicle captures, source coverage, registry projections and structural command evidence. They include allowlisted normalized technical values, competing source captures, recent charging receipts and correlated command history, not raw responses or a full request timeline. Unknown quota is neither zero nor unlimited. The quota sensor shows the last server-reported allowance in the current runtime, not a running balance. Read and command counters are separate. A reported allowance is not a guarantee of permission; after restart the current allowance remains unknown until a fresh header arrives. Active server restrictions are respected. Trip history is retained and the normal trip refresh deadline survives restart. Modern app last-trip averages use final display units (never legacy tenths); explicit per-100 units or consistent same-record totals also establish the scale. Unknown units and inconsistent ambiguous averages are not published; direct OEM totals remain separate from averages. Long-term totals are the current resettable window, not lifetime odometer statistics.
