# V3 feature closure and release acceptance

**Current decision: B43 development; release HOLD and stable NO GO.** B42 remains the published test baseline. Issue [#44](https://github.com/npinguin/audi_connect_ha/issues/44) owns stable acceptance. This document records evidence and unresolved gates; [V3 review](V3_REVIEW.md) is the current user/engineering guide.

## Existing authoritative inventories

- [V2 parity baseline](V2_V3_PARITY_BASELINE.json): 109 historical entity slots, 9 platforms, 11 services, 11 execute-action choices and 19 control workstreams. The baseline is a historical snapshot, not a current generated inventory.
- [Product entity contract](../custom_components/audiconnect/v3/product_entities.json): native HA identities, metadata references and declared product extensions.
- [Capability catalog](../custom_components/audiconnect/v3/full_catalog.json): executable operation variants; applicability and evidence are separate.
- [Ownership](../governance/OWNERSHIP.json): responsibility and architecture constraints.

Do not reproduce these inventories in a second editable catalog. A declared row is not evidence that its implementation works on a real vehicle.

## B43 implementation and acceptance evidence

B43 integrates onboarding #52, Data Act #59, source continuity #61, truthful charging state #62, quota #63, discovery #64, request priorities #65, command receipts #66, quota recovery #67, shared display selector #68, HA test compatibility #69, route revision and climate input closure #70, and quota-deferred native reads #71. See umbrella PR [#60](https://github.com/npinguin/audi_connect_ha/pull/60) for exact implementation and remaining audit work. The combined #71 candidate passed Test #2174 and Validate #2175 on HA 2026.7.4 and 2026.11.1 (historical evidence). Current policy tests only the latest stable HA monthly release, pinned to its latest stable patch. Command preparation uses one native budget for the complete necessary CARIAD or MBB sequence. Automated checks do not establish physical execution, the actual Audi quota scope or readiness for release. B43 closure retains the existing native scan interval, with quota-aware deferral; faster adaptive polling and multi-client optimization require measured OEM behavior rather than guessed thresholds.

### Q5 field evidence — charging remains open

- [B35 physical test](https://github.com/audiconnect/audi_connect_ha/pull/918#issuecomment-6877274976): tester reports successful START and STOP on a 2020 Q5 55 TFSI e, independently confirmed by approximately 2 kW while charging and 4.4 W after STOP. Smart charging was enabled. 1,000 trips were retained.
- [B39 field report](https://github.com/audiconnect/audi_connect_ha/pull/918#issuecomment-6880663863): STOP accepted (HTTP 200) but the vehicle continued charging; HA sometimes showed Off. Five historical entities were reported as no longer provided. Stale data and missing ETA require explicit interpretation, not fabricated values.
- [B40 retest, 14 November 2026](https://github.com/audiconnect/audi_connect_ha/pull/918#issuecomment-6881591226): with the timer disabled, STOP at 18:22:08 CET returned HTTP 200/accepted_unconfirmed, but physical power remained approximately 2 kW. myAudi reported timeout E.PA.VCF.18. Last reported charging was true, captured at 18:20:26 CET, before dispatch. HA Off was optimistic. Two diagnostics and an error screenshot are available in the upstream comment.

B43 corrects the false charging state projection and preserves known mutation receipts, but does not resolve the physical STOP root cause. Do not attribute the failure to timers, a changed route or Audi alone without comparing the before/after diagnostics and actual B35/B40 execution evidence. Do not blindly retry or change endpoints. Confirm the physical result separately with vehicle/myAudi/power evidence. Both B40 snapshots have now been analyzed. The actual STOP operation is `cariad.charging.stop`; HTTP 200 accepted_unconfirmed, last vehicle capture 18:20:26, subsequent cloud observation 18:22:23 still pre-dispatch. Quota remaining 45. Charging request array contains structural status/operation evidence but no verified correlation or actual values in exported diagnostics. B41 reuses the existing bounded request parser for charging; no extra API calls or physical-state inference. All five reported missing sensors were registered but not projected, and all 1,000 trips remained intact. Q5 target temperature C/F was not observed; the available climate routes were catalog matches with zero locally verified controls. Wake/refresh were untested; Data Act was not configured. Test myAudi STOP independently and compare a separate explicitly woken charging session; no automatic wake or retry. Test climate stored/parameterized/independent setpoint separately using native setup or Workbench before optional Data Act activation. The physical cause remains open. [Third B40 diagnostic and field report](https://github.com/audiconnect/audi_connect_ha/pull/918#issuecomment-6881920047): remote STOP timed out, charging continued at 2 kW, the user stopped manually around 18:30 CET and the later capture incorrectly promoted the remote command to verified. B41 separates actual vehicle projection, correlated backend result and matching readback timestamp; discovery always requires explicit physical confirmation. Charge-mode lists alternated empty/nonempty without an own capture; B41 removes sibling timestamp inheritance, retains historical mode evidence and fails closed on unordered conflicts. The cause of the OEM list fluctuation is not proven. B41 recovery uses the existing explicit physical discovery and revision-scoped per-mode verification; undated lists do not gain artificial capture timestamps. Previously registered native control identities survive reload without bypassing dispatch gates. Late historical scalar observations can populate last-known without replacing current state. Climate pending temperature feedback comes from the command journal, not an entity-local dispatched cache.
